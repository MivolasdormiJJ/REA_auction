# Руководство по стилю команды REA Auction

Практическая работа № 3, вариант 3. Документ обязателен для всех участников бригады и применяется
при написании кода и на code review. Ссылаться на пункты руководства в замечаниях нужно по их
номеру, например: «нарушен п. 1.4».

Руководство опирается на общепринятые нормы языков проекта:

| Область | Базовый стандарт | Инструмент проверки |
|---|---|---|
| Python / Django (`auction/`, `config/`) | [PEP 8](https://peps.python.org/pep-0008/), [Django coding style](https://docs.djangoproject.com/en/5.2/internals/contributing/writing-code/coding-style/) | `ruff check`, `ruff format` (настройки в `pyproject.toml`) |
| TypeScript / React (`frontend/src/`) | [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/), [React Rules](https://react.dev/reference/rules) | `oxlint`, `tsc -b`, Prettier (`frontend/.prettierrc.json`) |
| Все файлы | — | `.editorconfig` |

Если пункт руководства противоречит базовому стандарту, действует руководство.

## 1. Форматирование кода: отступы и переносы строк

### 1.1. Отступы

| Тип файла | Отступ |
|---|---|
| `*.py` | 4 пробела |
| `*.ts`, `*.tsx`, `*.css`, `*.json`, `*.yml`, `*.html` | 2 пробела |
| `Makefile`, `Dockerfile` (`RUN` с продолжением) | 4 пробела |

- Табуляция запрещена во всех файлах. Смешивание табов и пробелов — ошибка.
- Отступ продолжения (hanging indent) — один уровень (4 / 2 пробела), выравнивание «по открывающей скобке» не используется.
- Настройки зафиксированы в `.editorconfig`, IDE обязана его учитывать (VS Code — расширение *EditorConfig*, PyCharm/WebStorm — встроено).

### 1.2. Длина строки

- Python — не более **100** символов; TypeScript/TSX — не более **100** символов.
- Исключения: URL в комментариях, длинные строковые литералы сообщений, которые нельзя разбить без потери смысла (помечаются `# noqa: E501`).
- Markdown-документация — без жёсткого ограничения, но одно предложение на строку приветствуется.

### 1.3. Правила переноса

Переносим по скобкам, а не обратным слешем. Если вызов не помещается в строку — каждый аргумент
на отдельной строке и завершающая запятая:

```python
# Плохо
return Response({"id": user.pk, "username": user.username, "can_moderate": user.has_perm("auction.moderate_auction"), "is_admin": user.is_superuser})

# Хорошо
return Response(
    {
        "id": user.pk,
        "username": user.username,
        "can_moderate": user.has_perm("auction.moderate_auction"),
        "is_admin": user.is_superuser,
    }
)
```

- Бинарные операторы (`and`, `or`, `+`, `|`, `&&`, `||`) ставятся **в начале** перенесённой строки.
- Цепочки вызовов (Django QuerySet, Promise) — по одному методу на строке, оборачиваем в скобки:

```python
bids = (
    Bid.objects.filter(auction=auction)
    .select_related("bidder")
    .order_by("amount_kopecks", "created_at", "id")
)
```

- JSX: если у элемента больше двух props или строка длиннее лимита — каждый prop на отдельной строке,
  закрывающая `>` — на строке последнего prop'а. Многострочный JSX в `return` оборачивается в `( … )`.

### 1.4. Пустые строки

- Python: 2 пустые строки между определениями верхнего уровня (функции, классы), 1 — между методами класса.
  Внутри функций пустая строка отделяет логические шаги; больше одной подряд — запрещено.
- TypeScript: 1 пустая строка между функциями/компонентами верхнего уровня и между группами импортов.
- Файл заканчивается ровно одним символом перевода строки; хвостовые пробелы запрещены.

### 1.5. Импорты

Порядок групп, разделённых пустой строкой:

1. стандартная библиотека (`hashlib`, `json`) / встроенные модули Node;
2. сторонние пакеты (`django`, `rest_framework`; `react`, `antd`);
3. модули проекта (`.models`, `../api/client`).

Внутри группы — по алфавиту; один модуль импортируется одной инструкцией. Неиспользуемые импорты
запрещены (ruff `F401`, `noUnusedLocals` в TS). Для типов в TS — `import type`.

### 1.6. Кавычки, запятые, точки с запятой

| | Python | TypeScript |
|---|---|---|
| Строки | двойные `"…"` | одинарные `'…'`, в JSX-атрибутах — двойные |
| Завершающая запятая | в многострочных коллекциях и вызовах | там же (`trailingComma: "all"`) |
| Точка с запятой | — | обязательна |

### 1.7. Именование (кратко, т.к. влияет на читаемость отформатированного кода)

- Python: `snake_case` — функции и переменные, `PascalCase` — классы, `UPPER_SNAKE_CASE` — константы.
- TS: `camelCase` — функции и переменные, `PascalCase` — компоненты, типы, файлы компонентов (`AuctionDetailPage.tsx`).
- Однобуквенные имена допустимы только для индексов циклов и лямбд в одну строку. `a`, `s`, `b`, `u`
  для аукциона, сериализатора, ставки, пользователя — запрещены: пишем `auction`, `serializer`, `bid`, `user`.

### 1.8. Комментарии

- Язык комментариев и docstring — русский, единообразно по всему проекту.
- Комментарий объясняет **почему**, а не **что**. Принятый в проекте формат для неочевидных решений:

```python
# ПРОБЛЕМА: <что могло сломаться>.
# РЕШЕНИЕ: <как код это предотвращает>.
```

- Закомментированный код в репозиторий не коммитится.

### 1.9. Автоматизация

```bash
# Python: проверка и автоформат
ruff check auction config
ruff format auction config

# Frontend
cd frontend
npm run lint
npx prettier --check "src/**/*.{ts,tsx,css}"
```

Ручное форматирование не обсуждается на code review — если форматтер пропустил код, он корректен.

## 2. Разделение функционала на независимые модули и компоненты

### 2.1. Слои backend

Каждый слой знает только о слоях ниже себя:

```
views.py / admin_api.py / notifications.py   ← HTTP: разбор запроса, права, ответ
        │
serializers.py                               ← валидация входных данных, представление
        │
services.py                                  ← бизнес-правила, транзакции, блокировки
        │
models.py                                    ← схема данных, ограничения БД
```

- **models.py** — только поля, `Meta`, ограничения целостности, простые свойства. Без HTTP и без бизнес-сценариев.
- **services.py** — вся бизнес-логика: ставки, переходы статусов, закрытие торгов. Функции сервисов
  принимают идентификаторы и примитивы, а не `request`; бросают доменные исключения (`Conflict`, `Locked`).
  Именно сервисы тестируются в первую очередь.
- **serializers.py** — проверка формы данных; бизнес-инварианты (например, «одна ставка на участника») здесь не проверяются.
- **views.py** — тонкий слой: разобрать запрос → вызвать сервис → вернуть ответ. Правило: если в
  view появляется `select_for_update()` или ветвление по статусу аукциона, логика переносится в `services.py`.
- **management/commands/** — только вызов сервисов; своя логика запрещена (команда `close_auctions` вызывает `services.close_auction`).

### 2.2. Слои frontend

```
pages/        ← страница = маршрут; собирает компоненты, держит состояние страницы
components/   ← переиспользуемые UI-элементы без обращения к API
context/      ← глобальное состояние (AuthContext)
api/          ← HTTP-клиент и функции запросов; типы ответов в api/types.ts
utils/        ← чистые функции (форматирование денег и дат), без React и без HTTP
```

- Компонент из `components/` не импортирует `api/` и не знает о маршрутах — данные получает через props.
- Страница не вызывает `axios` напрямую — только функции из `api/*.ts`.
- Код, который повторяется в двух и более местах (например, форматирование копеек в рубли), выносится в `utils/` или `components/`.
- Один файл — один экспортируемый компонент (правило `react/only-export-components`).
- Ориентир по размеру: файл длиннее **250 строк** или компонент с более чем **8 `useState`** — кандидат на разбиение
  (выделить подкомпоненты, хук `useXxx` или форму).

### 2.3. Правила зависимостей между модулями

- Циклические импорты запрещены (`services` ↔ `views`, `pages` ↔ `components`).
- Модуль экспортирует минимальный публичный интерфейс; внутренние функции Python начинаются с `_`.
- Константы предметной области (статусы аукциона, права) берутся из одного источника:
  `Auction.Status.OPEN` вместо строки `"open"`; на фронтенде — union-тип `AuctionStatus` из `api/types.ts`.
- Новое Django-приложение создаётся, если функциональность имеет собственные модели и может быть
  отключена без поломки аукционов (например, будущие платежи — `payments/`).

### 2.4. Тесты следуют модулям

- Тесты backend лежат рядом с кодом: `auction/test_<модуль>.py`; один файл тестов — один модуль/сценарий.
- Каждая новая функция в `services.py` сопровождается тестом.

## 3. Управление зависимостями и версиями библиотек

### 3.1. Где объявляются зависимости

| Экосистема | Манифест | Lock-файл | Установка |
|---|---|---|---|
| Python | `requirements.txt` | — (см. 3.4) | `pip install -r requirements.txt` |
| Node | `frontend/package.json` | `frontend/package-lock.json` | только `npm ci` в CI и Docker |
| Окружение | `Dockerfile`, `.github/workflows/*.yml` | — | — |

- Версии рантаймов фиксированы и совпадают везде: **Python 3.12**, **Node 22**, **PostgreSQL 16**.
  Изменение версии рантайма — отдельный PR, который меняет `Dockerfile`, `compose.yaml` и CI одновременно.

### 3.2. Указание версий

- Python: диапазон с верхней границей по совместимой ветке — `Django>=5.2,<5.3`, `gunicorn>=23,<24`.
  Зависимость без верхней границы (`psycopg[binary]>=3.3`) запрещена.
- Node: `dependencies` — `^` (минорные обновления), `typescript` — `~` (только патчи, т.к. минорные версии TS ломают типы).
- `package-lock.json` всегда коммитится вместе с изменением `package.json`. Ручная правка lock-файла запрещена.
- Сервисы в `compose.yaml` и CI указываются с тегом мажорной версии (`postgres:16`), не `latest`.
- GitHub Actions подключаются с мажорной версией (`actions/checkout@v4`).

### 3.3. Добавление новой зависимости

Перед добавлением автор PR в описании отвечает на вопросы:

1. Нельзя ли решить задачу стандартной библиотекой или уже подключённым пакетом?
2. Лицензия совместима (MIT, BSD, Apache-2.0)?
3. Пакет поддерживается: релиз за последний год, нет открытых критических уязвимостей?
4. Каков размер для фронтенда (bundle size)?

Dev-зависимости (линтеры, типы) — в `devDependencies` / отдельный `requirements-dev.txt`, а не в production-образ.

### 3.4. Воспроизводимость сборки Python

Для production-образа рекомендуется генерировать зафиксированный список:

```bash
pip install pip-tools
pip-compile requirements.txt -o requirements.lock
```

Пока lock-файл не введён, CI обязан собираться на чистом окружении при каждом push, чтобы новая минорная
версия библиотеки, сломавшая сборку, обнаруживалась сразу.

### 3.5. Обновление зависимостей

- Автоматические PR на обновление создаёт Dependabot (`.github/dependabot.yml`) раз в неделю, сгруппированно.
- Патч- и минорные обновления сливаются после зелёного CI.
- Мажорные обновления (Django 5→6, React 19→20, antd 6→7) — отдельная задача: чтение changelog / migration guide,
  ручная проверка ключевых сценариев (регистрация, создание задачи, ставка, закрытие торгов).
- Уязвимости: `pip-audit` и `npm audit --omit=dev` запускаются перед каждым релизом; high/critical исправляются до релиза.

## 4. Обновление и поддержка программного обеспечения после выпуска

### 4.1. Версионирование

Проект использует [Semantic Versioning](https://semver.org/lang/ru/) `MAJOR.MINOR.PATCH`:

- **MAJOR** — несовместимое изменение API (`docs/API.md`) или схемы, требующее ручной миграции данных;
- **MINOR** — новая функциональность с обратной совместимостью;
- **PATCH** — исправление ошибок.

Версия фиксируется git-тегом `vX.Y.Z` на коммите в `main` и записью в `CHANGELOG.md`
(формат [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/)).

### 4.2. Ветки

| Ветка | Назначение |
|---|---|
| `main` | выпущенные версии, только через PR |
| `dev_any` | интеграционная ветка, автодеплой на Render |
| `feature/<кратко>`, `labN_<имя>` | разработка задачи |
| `hotfix/<версия>` | срочное исправление выпущенной версии, ответвляется от тега |

Hotfix сливается в `main` (новый PATCH-тег) **и** обратно в `dev_any`.

### 4.3. Сообщения коммитов

[Conventional Commits](https://www.conventionalcommits.org/ru/): `тип(область): описание`.
Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `deps`. Пример: `fix(bids): запретить ставку после ends_at`.
Это позволяет собирать `CHANGELOG.md` по истории.

### 4.4. Миграции базы данных

- Миграции только **вперёд-совместимые**: сначала добавить nullable-поле и код, работающий с обоими вариантами,
  в следующем релизе — сделать поле обязательным / удалить старое.
- Удаление и переименование полей — только в MAJOR-релизе или в два шага.
- CI проверяет, что миграции не забыты: `python manage.py makemigrations --check --dry-run`.
- Перед применением миграций в production делается резервная копия БД (`pg_dump`).

### 4.5. Выпуск и откат

Чек-лист релиза:

1. CI зелёный в `dev_any`; `pip-audit` и `npm audit` без high/critical.
2. Обновлён `CHANGELOG.md`, раздел `[Unreleased]` переименован в версию.
3. PR `dev_any → main` прошёл review минимум одного участника.
4. Создан тег `vX.Y.Z`.
5. После деплоя — smoke-проверка: вход, каталог, ставка на тестовом аукционе.

Откат: повторный деплой предыдущего тега на Render. Если релиз содержал миграцию — откат только при её
обратной совместимости (п. 4.4), иначе выпускается hotfix.

### 4.6. Поддержка

- Ошибки регистрируются как GitHub Issues с шаблоном: шаги воспроизведения, ожидаемый/фактический результат, версия.
- Приоритеты: **P0** (данные/деньги/безопасность, исправление в течение суток через hotfix),
  **P1** (ключевой сценарий не работает, следующий PATCH), **P2** (остальное, плановый MINOR).
- Каждое исправление ошибки сопровождается регрессионным тестом.
- Поддерживается только последняя MINOR-версия; исправления в старые версии не переносятся.
- Устаревающая функциональность API помечается в `docs/API.md` как *deprecated* и удаляется не раньше следующего MAJOR.

## 5. Процесс code review

1. Автор открывает PR, заполняет шаблон (`.github/pull_request_template.md`), прогоняет линтеры и тесты локально.
2. Ревьюер проверяет PR по чек-листу шаблона, оставляет замечания со ссылкой на пункт руководства.
3. Метки замечаний: **[блокер]** — нарушение руководства или ошибка, без исправления слияние запрещено;
   **[замечание]** — желательно исправить в этом PR; **[вопрос]**; **[nit]** — мелочь на усмотрение автора.
4. PR сливается после одобрения минимум одного ревьюера и зелёного CI.
5. Размер PR — ориентировочно до 400 строк изменений; больше — разбить.

Пример проведённого review — [docs/CODE_REVIEW.md](CODE_REVIEW.md).
