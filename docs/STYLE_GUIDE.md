# Руководство по стилю проекта «Система обратных аукционов»

Документ обязателен для всех участников бригады. Он задаёт единые правила для
серверной части (Python 3.12, Django 5.2, DRF 3.16) и клиентской части
(TypeScript, React 19, Ant Design 6, Vite).

Основы, на которые мы опираемся:

- Python: [PEP 8](https://peps.python.org/pep-0008/), форматтер
  [Black](https://black.readthedocs.io/), линтер [Ruff](https://docs.astral.sh/ruff/);
- TypeScript/React: [Airbnb JavaScript Style Guide](https://github.com/airbnb/javascript)
  в части, не противоречащей [Prettier](https://prettier.io/), линтер oxlint;
- версии: [Semantic Versioning 2.0.0](https://semver.org/lang/ru/),
  коммиты: [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/).

Если правило из этого документа расходится со сторонним руководством,
действует этот документ. Если автоматический форматтер и документ расходятся,
действует форматтер: спорить с инструментом на ревью запрещено.

Уровни требований:

- **ОБЯЗАТЕЛЬНО** — нарушение блокирует слияние PR;
- **РЕКОМЕНДУЕТСЯ** — ревьюер может попросить исправить, автор может
  обоснованно отказаться.

## 1. Форматирование кода: отступы и переносы строк

### 1.1. Общие правила для всех файлов

Правила закреплены в [`.editorconfig`](../.editorconfig) в корне репозитория,
его подхватывают VS Code, PyCharm и WebStorm.

| Параметр              | Python | TS / TSX / JSON / CSS | YAML  | Markdown |
| --------------------- | ------ | --------------------- | ----- | -------- |
| Отступ                | 4 пробела | 2 пробела          | 2 пробела | 2 пробела |
| Максимальная длина строки | 88 | 100                    | —     | —        |
| Символ конца строки   | LF     | LF                    | LF    | LF       |
| Кодировка             | UTF-8  | UTF-8                 | UTF-8 | UTF-8    |

**ОБЯЗАТЕЛЬНО:**

1. Табуляция для отступов запрещена, только пробелы.
2. В конце строк нет пробелов, файл заканчивается одним переводом строки.
3. Концы строк только LF. На Windows задайте `git config core.autocrlf input`.
4. Перед коммитом код прогоняется форматтером:
   - backend: `black .` и `ruff check .` (настройки в [`pyproject.toml`](../pyproject.toml));
   - frontend: `npm run format` и `npm run lint` (настройки в
     [`frontend/.prettierrc.json`](../frontend/.prettierrc.json)).

### 1.2. Python

**Отступы.** Один уровень вложенности равен 4 пробелам. Продолжение строки
оформляется *висячим отступом* внутри скобок. Обратный слэш `\` для переноса
не используется.

```python
# Плохо: перенос обратным слэшем и выравнивание «на глаз»
a.payment_kopecks = best[1].amount_kopecks \
                    if len(best) > 1 else a.budget_kopecks

# Хорошо: скобки и висячий отступ
auction.payment_kopecks = (
    best[1].amount_kopecks if len(best) > 1 else auction.budget_kopecks
)
```

**Переносы длинных вызовов.** Если аргументы не помещаются в 88 символов,
каждый аргумент пишется на отдельной строке, после последнего ставится
запятая (*magic trailing comma*). Тогда добавление аргумента меняет одну
строку в diff, а не три.

```python
# Хорошо
bid = Bid.objects.create(
    auction=auction,
    bidder=user,
    amount_kopecks=amount,
    idempotency_key=key,
)
```

**Логические операторы** при переносе ставятся в начале строки (как в PEP 8
и Black), а не в конце:

```python
return bool(
    request.user.is_authenticated
    and request.user.is_active
    and request.user.email_verified
)
```

**Пустые строки:**

- 2 пустые строки между функциями и классами верхнего уровня;
- 1 пустая строка между методами класса;
- внутри функции пустой строкой отделяются логические шаги (валидация →
  работа с БД → ответ), но не каждая строка.

**Импорты** делятся на три группы, между группами одна пустая строка, внутри
группы порядок алфавитный (проверяется правилом Ruff `I`):

```python
# 1. Стандартная библиотека
from datetime import timedelta

# 2. Сторонние пакеты
from django.db import transaction
from rest_framework.exceptions import ValidationError

# 3. Модули проекта
from .models import Auction, Bid
```

Импорт внутри функции разрешён только для разрыва циклической зависимости
и сопровождается комментарием, почему он там.

### 1.3. TypeScript и React

**Отступы** 2 пробела, длина строки 100, одинарные кавычки, точка с запятой
обязательна, запятая после последнего элемента многострочных литералов.

**Длинные выражения** переносятся так же, как в Python: по одному элементу
на строку.

```tsx
// Плохо: 120 символов в строке
return (k / 100).toLocaleString('ru-RU', { style: 'currency', currency: 'RUB', maximumFractionDigits: 0 });

// Хорошо
return (kopecks / 100).toLocaleString('ru-RU', {
  style: 'currency',
  currency: 'RUB',
  maximumFractionDigits: 0,
});
```

**JSX.** Если у компонента больше двух пропсов или строка длиннее 100
символов, каждый проп пишется на своей строке, закрывающая `>` на отдельной
строке. Многострочный JSX оборачивается в круглые скобки.

```tsx
<Typography.Text
  type="secondary"
  style={{ marginLeft: 12 }}
>
  до {new Date(auction.ends_at).toLocaleString('ru-RU')}
</Typography.Text>
```

**Импорты** в порядке: React → сторонние библиотеки → модули проекта
(`../api`, `../components`, `../utils`) → стили. Типы импортируются через
`import type`.

## 2. Разделение функционала на независимые модули и компоненты

### 2.1. Принципы

1. **Одна ответственность.** Модуль, класс или компонент отвечает за одну
   задачу. Если его назначение нельзя описать одним предложением без «и»,
   его нужно разделить.
2. **Зависимости направлены в одну сторону.** Верхний слой знает о нижнем,
   нижний о верхнем не знает.
3. **Повторное использование вместо копирования.** Код, повторённый во
   втором месте, выносится в общий модуль (правило «двух повторов»).
4. **Явный публичный интерфейс.** Функции, предназначенные только для
   внутреннего использования модуля, начинаются с `_` (Python) или
   не экспортируются (TypeScript).

### 2.2. Слои backend (Django)

```
HTTP-запрос
   │
   ▼
views.py        — разбор запроса, права доступа, формирование ответа
   │
   ├──► serializers.py — валидация входных данных и сериализация ответа
   ▼
services.py     — бизнес-правила: ставки, модерация, закрытие торгов
   │
   ▼
models.py       — структура данных, choices, ограничения БД
```

| Модуль                  | Можно                                    | Нельзя                                   |
| ----------------------- | ---------------------------------------- | ---------------------------------------- |
| `models.py`             | поля, `Meta`, `choices`, простые свойства | импортировать views, serializers, services |
| `serializers.py`        | валидация формата и диапазонов           | транзакции, изменение чужих объектов     |
| `services.py`           | транзакции, блокировки, переходы статусов, запись событий | работать с `request`, возвращать `Response` |
| `views.py`              | вызывать сервисы и сериализаторы         | содержать бизнес-правила (проверки бюджета, сроков, статусов) |
| `management/commands/`  | вызывать сервисы                         | дублировать логику сервисов              |

**ОБЯЗАТЕЛЬНО:**

- Статусы и другие перечисления берутся из `models.TextChoices`
  (`Auction.Status.OPEN`), строковые литералы `"open"` в коде запрещены.
  Литерал не ловится проверкой и ломается молча при переименовании.
- Имена переменных отражают сущность: `auction`, `serializer`, `user`.
  Однобуквенные имена (`a`, `s`, `u`) допустимы только для индексов и
  лямбд в одну строку.
- Новое Django-приложение заводится, когда появляется самостоятельная
  предметная область (например, `payments`), а не для отдельной модели.

### 2.3. Структура frontend

```
src/
├── api/          — HTTP-клиент и функции запросов; типы ответов (types.ts)
├── components/   — переиспользуемые UI-компоненты без обращения к API
├── context/      — глобальное состояние (авторизация)
├── pages/        — страницы-маршруты: собирают компоненты и вызывают api/
├── utils/        — чистые функции без React и сети (форматирование и т. п.)
├── App.tsx       — маршрутизация
└── main.tsx      — точка входа
```

Разрешённые направления импорта:

```
pages ──► components ──► utils
  │           │
  └──► api ◄──┘ (только типы из api/types)
  └──► context ──► api
```

**ОБЯЗАТЕЛЬНО:**

- Страницы и компоненты не импортируют `axios` напрямую: все запросы идут
  через функции из `src/api/`. Это позволяет менять клиент, CSRF-логику и
  адреса API в одном месте.
- `components/` не зависят от `pages/`.
- `utils/` не импортируют React и не обращаются к сети, поэтому их легко
  тестировать.
- Один файл — один экспортируемый компонент. Имя файла совпадает с именем
  компонента в PascalCase (`StatusBadge.tsx`).
- Компонент длиннее ~200 строк рассматривается на ревью как кандидат на
  разделение (**РЕКОМЕНДУЕТСЯ**).

## 3. Управление зависимостями и версиями библиотек

### 3.1. Где описаны зависимости

| Часть      | Файл                       | Назначение                                 |
| ---------- | -------------------------- | ------------------------------------------ |
| Backend    | `requirements.txt`         | зависимости, нужные для работы приложения |
| Backend    | `requirements-dev.txt`     | инструменты разработки (black, ruff); подключает `requirements.txt` |
| Frontend   | `frontend/package.json`    | `dependencies` и `devDependencies`         |
| Frontend   | `frontend/package-lock.json` | точные версии всего дерева зависимостей  |
| Окружение  | `Dockerfile`, `compose.yaml` | версии Python и PostgreSQL               |

### 3.2. Правила указания версий

**Python.** Версия ограничивается снизу проверенной версией и сверху
следующей несовместимой:

```text
# Плохо: следующая мажорная версия установится без проверки
psycopg[binary]>=3.3

# Хорошо: обновления исправлений принимаются, мажорные — только вручную
psycopg[binary]>=3.3,<4.0
Django>=5.2,<5.3
```

Для Django используется ограничение на минорную версию (LTS-ветка 5.2), для
остальных пакетов — на мажорную.

**JavaScript.** В `package.json` используется `^` (совместимые обновления
по SemVer). Для пакетов в версии `0.x` и для TypeScript используется `~`,
потому что у них несовместимые изменения бывают и в минорных версиях.

**Docker.** Базовые образы указываются с конкретной версией
(`python:3.12-slim`, `postgres:16`), тег `latest` запрещён.

### 3.3. Lock-файлы

- `package-lock.json` **ОБЯЗАТЕЛЬНО** коммитится. В CI и Docker зависимости
  ставятся командой `npm ci`, которая устанавливает ровно то, что в lock-файле.
- Lock-файл не редактируется руками. Конфликт в нём решается так: принять
  версию из `main`, затем заново выполнить `npm install`.
- Изменение `package.json` без соответствующего изменения
  `package-lock.json` (и наоборот) на ревью не принимается.

### 3.4. Добавление новой зависимости

Перед добавлением библиотеки автор PR проверяет и пишет в описании PR:

1. зачем она нужна и почему задачу нельзя решить имеющимися средствами;
2. лицензию (допускаются MIT, BSD, Apache-2.0, ISC);
3. активность поддержки: последний релиз не старше года;
4. размер (для frontend) и количество транзитивных зависимостей.

Инструменты разработки ставятся только в `devDependencies` или
`requirements-dev.txt`. Неиспользуемые зависимости удаляются.

### 3.5. Проверка безопасности

- `npm audit --omit=dev` и `pip-audit -r requirements.txt` запускаются перед
  каждым релизом.
- Уязвимость уровня high или critical исправляется до релиза.
- Обновления зависимостей предлагает Dependabot
  ([`.github/dependabot.yml`](../.github/dependabot.yml)) раз в неделю.

## 4. Обновление и поддержка программного обеспечения после выпуска

### 4.1. Версионирование релизов

Проект использует [SemVer](https://semver.org/lang/ru/): `МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ`.

| Что изменилось                                         | Какая часть растёт | Пример          |
| ------------------------------------------------------ | ------------------ | --------------- |
| Несовместимое изменение API (удалено поле, изменён URL) | МАЖОРНАЯ          | `1.4.2 → 2.0.0` |
| Новая функция без поломки старых клиентов              | МИНОРНАЯ           | `1.4.2 → 1.5.0` |
| Исправление ошибки                                     | ПАТЧ               | `1.4.2 → 1.4.3` |

Версия хранится в `frontend/package.json` (`version`) и в теге Git
`vX.Y.Z` на коммите релиза. До первого публичного релиза версия `0.x.y`.

### 4.2. Ветки

```
main ─────●──────────●──────────●───────►   всегда готов к выпуску, теги vX.Y.Z
           \        / \        /
feature/*   ●──●──●    \      /             новая функциональность
                        \    /
hotfix/*                 ●──●               срочное исправление релиза
```

- `main` защищена: прямой push запрещён, слияние только через PR с одним
  одобрением и зелёными тестами.
- `feature/<кратко-о-задаче>` создаётся от `main` для каждой задачи.
- `hotfix/<версия>-<суть>` создаётся от тега релиза для срочных исправлений.

### 4.3. Сообщения коммитов

Формат [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<тип>(<область>): <что сделано в повелительном наклонении>
```

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `build`, `chore`.
Несовместимое изменение отмечается `!` после типа (`feat(api)!: ...`).

```text
Плохо:  Added simple frontend
Хорошо: feat(frontend): add auction catalog and cabinet pages
Хорошо: fix(bids): reject bid equal to zero
```

### 4.4. Журнал изменений

Каждый PR, заметный пользователю, добавляет строку в раздел `[Unreleased]`
файла [`CHANGELOG.md`](../CHANGELOG.md) (формат
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/)). При выпуске раздел
переименовывается в номер версии с датой.

### 4.5. Процесс выпуска и исправления

1. Перед релизом: тесты проходят (`python manage.py test`), фронтенд
   собирается (`npm run build`), выполнен аудит зависимостей.
2. Обновить версию и `CHANGELOG.md`, слить в `main`, поставить тег `vX.Y.Z`.
3. **Срочное исправление (hotfix):** ветка от тега → исправление + тест,
   воспроизводящий ошибку → PR в `main` → ПАТЧ-версия.
4. Ошибки, найденные после выпуска, фиксируются в issue с шагами
   воспроизведения, ожидаемым и фактическим результатом.

### 4.6. Миграции базы данных

- Миграции создаются только командой `makemigrations` и коммитятся вместе
  с изменением модели.
- Применённые в релизе миграции не редактируются: исправление делается
  новой миграцией.
- Удаление поля выполняется в два релиза: сначала код перестаёт его
  использовать, затем следующей версией поле удаляется. Так старая и новая
  версии приложения могут работать с одной БД во время обновления.
- Файлы баз данных (`db.sqlite3`) и пользовательские данные в репозиторий
  не попадают.

### 4.7. Поддержка API

- Удаляемый или изменяемый эндпоинт сначала помечается устаревшим в
  `docs/API.md` и продолжает работать минимум одну минорную версию.
- Изменения в контракте API отражаются в `docs/API.md` в том же PR.

### 4.8. Плановое обслуживание

| Действие                                   | Периодичность      |
| ------------------------------------------ | ------------------ |
| Разбор PR от Dependabot                    | еженедельно        |
| `npm audit`, `pip-audit`                   | перед каждым релизом |
| Обновление Django в пределах LTS 5.2       | при выходе патча безопасности |
| Пересмотр этого руководства                | раз в семестр / по запросу команды |

## 5. Code review

Каждый PR проходит ревью хотя бы одного участника, не являющегося автором.
Чек-лист ревьюера встроен в шаблон PR
([`.github/pull_request_template.md`](../.github/pull_request_template.md)) и
соответствует разделам 1–4 этого документа.

Правила общения на ревью:

- комментарий относится к коду, а не к автору;
- замечание ссылается на пункт руководства (например, «см. 2.2: статус
  литералом»);
- необязательные пожелания помечаются префиксом `nit:`;
- автор отвечает на каждое замечание: исправлением или аргументом.
