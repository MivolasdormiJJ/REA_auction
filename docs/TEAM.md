# Распределение работ в команде REA Auction

## Кратко о проекте

**REA Auction** — платформа **обратных аукционов** для студенческих задач. Заказчик публикует
задачу с бюджетом, исполнители делают **одну закрытую от изменения ставку** — сколько они
хотят получить. Побеждает **минимальная** ставка, а платят победителю **вторую по величине цену**
(правило Викри, «второй цены»): так каждому выгодно ставить свою честную цену.
Если ставка одна — платится весь бюджет.

Жизненный цикл аукциона:

```
draft (черновик) ──submit──▶ review (модерация) ──approve──▶ open (приём ставок)
      ▲                            │                              │ время ends_at вышло
      └──── правка ◀── rejected ◀──┘ reject                       ▼
                                                     closed (победитель + цена)
                                                     или paused (участник заблокирован)
                                                              │
                         Работа: in_progress → submitted → revision_requested → … → accepted
```

## Архитектура подробно: MVC

### Архитектурный стиль проекта

Проект построен по шаблону **MVC (Model — View — Controller)** в том варианте, который принят в Django
и называется **MTV (Model — Template — View)**. Поверх него выделен **сервисный слой**, а представление
вынесено в отдельное **клиентское приложение (SPA)**. Итого три уровня описания:

1. **Клиент-серверная архитектура:** браузер с React-приложением ⇄ REST API на Django ⇄ PostgreSQL.
2. **MVC на сервере:** модели — `models.py`, контроллеры — `views.py` и другие `*_api.py`, представление — JSON через сериализаторы.
3. **Разделение на слои внутри сервера:** контроллер → сервис → модель; каждый слой обращается только к слою ниже.

### Как MVC соответствует Django и нашему коду

В Django названия сдвинуты: то, что в классическом MVC называется *Controller*, в Django называется *View*,
а *View* классического MVC — это *Template*. Поэтому на защите важно не путаться:

| Классический MVC | Django (MTV) | В нашем проекте | Отвечает за | Чего **не** делает |
|---|---|---|---|---|
| **Model** | Model | `auction/models.py`, `auction/task_completion.py` + бизнес-логика `auction/services.py` | данные, их связи, ограничения целостности, правила предметной области | не знает про HTTP, JSON, кнопки |
| **View** (представление) | Template | React-приложение `frontend/src/` + сериализаторы `auction/serializers.py` (формируют JSON) | показ данных пользователю, формат ответа | не меняет данные сам, не проверяет права |
| **Controller** | View | `auction/views.py`, `work_api.py`, `analytics.py`, `notifications.py`, `admin_api.py`; маршрутизатор `config/urls.py` | принимает запрос, проверяет права, вызывает модель/сервис, выбирает ответ | не хранит бизнес-правила (они в `services.py`) |

Шаблоны Django (`TEMPLATES` в `config/settings.py`) в проекте используются только встроенной админкой
`/django-admin/`. Пользовательский интерфейс целиком на React: сервер отдаёт один `index.html`
(функция `frontend_app` в `config/urls.py`), дальше страницы рисует браузер, а данные приходят в JSON.

### Model подробно

**Model** у нас состоит из двух частей.

**1. Модели данных (`auction/models.py`)** — описание таблиц через Django ORM:

```
                 ┌────────────┐
                 │  Category  │  24 направления подготовки
                 └─────┬──────┘
                       │ 1:N
┌──────────┐  owner  ┌─▼─────────────────────┐  1:N   ┌───────────────────┐
│   User   │◀────────│        Auction        │───────▶│        Bid        │
│ (Abstract│  winner │ status, budget_kopecks│        │ amount_kopecks    │
│   User)  │◀────────│ ends_at, due_at       │        │ idempotency_key   │
│ email    │         │ payment_kopecks       │        └─────────┬─────────┘
│ email_   │         └──┬──────────┬───────┬─┘                  │ bidder → User
│ verified │            │1:N       │1:1    │1:1
└──────────┘     ┌──────▼───┐ ┌────▼─────┐ ┌▼───────────────┐
                 │  Event   │ │WorkOrder │ │ TaskCompletion │
                 │ журнал   │ │ status   │ │ confirmed_by   │
                 │ действий │ └────┬─────┘ └────────────────┘
                 └──────────┘      │1:N
                         ┌─────────▼──────────┐   ┌──────────────────┐
                         │  WorkSubmission    │   │ AuctionRequest   │
                         │ revision_number    │   │ owner + key →    │
                         │ review_status      │   │ созданный Auction│
                         └────────────────────┘   └──────────────────┘
```

Целостность гарантирует сама база, а не только код:

| Ограничение | Модель | Смысл |
|---|---|---|
| `budget_min_ruble` | `Auction` | бюджет не меньше 1 ₽ (100 копеек) |
| `due_after_auction` | `Auction` | срок сдачи работы позже окончания торгов |
| `one_bid_per_person` | `Bid` | одна ставка на участника в аукционе |
| `unique_request_key`, `unique_auction_create_key` | `Bid`, `AuctionRequest` | повтор запроса с тем же ключом не создаёт дубль |
| `bid_positive` | `Bid` | ставка больше нуля |
| `work_unique_revision`, `work_unique_submission_key` | `WorkSubmission` | номера версий работы не повторяются |
| `on_delete=PROTECT` | все связи | нельзя удалить пользователя или аукцион, у которых есть история |

**2. Бизнес-логика (`auction/services.py`)** — правила предметной области, вынесенные из контроллеров
(шаблон *Service Layer*). Каждая функция принимает идентификаторы и пользователя, а не HTTP-запрос,
поэтому её одинаково вызывают и контроллер, и фоновая команда, и тесты:

| Функция | Что делает | Как защищена |
|---|---|---|
| `place_bid` | принимает ставку | `@transaction.atomic`, `select_for_update()` аукциона и пользователя |
| `transition` | переходы `submit` / `approve` / `reject` (конечный автомат статусов) | разрешены только явно перечисленные действия и переходы |
| `close_auction` | закрывает торги, выбирает победителя и считает вторую цену | блокирует всех участников в одном порядке (`order_by('pk')`), чтобы не было взаимной блокировки |
| `event` | пишет запись в журнал `Event` | вызывается из каждого перехода — получается журнал аудита |
| `Conflict`, `Locked` | доменные исключения | DRF превращает их в HTTP 409 и 423 |

### Controller подробно

Контроллеры — это функции и классы, которые принимают HTTP-запрос. Их «точка входа» — маршрутизатор
`config/urls.py` (шаблон *Front Controller*): все URL проекта описаны в одном месте.

| Контроллер | Тип | URL | Назначение |
|---|---|---|---|
| `AuctionViewSet` (`views.py`) | `ModelViewSet` DRF | `GET/POST /api/auctions/`, `GET/PATCH /api/auctions/{id}/` | список с фильтрами и поиском, создание, просмотр, правка черновика |
| ↳ `@action` методы | доп. действия | `POST …/{id}/submit/`, `…/approve/`, `…/reject/`, `GET/POST …/{id}/bids/` | модерация и ставки |
| `CategoryViewSet` (`views.py`) | `ReadOnlyModelViewSet` | `GET /api/categories/` | справочник категорий |
| `register`, `signin`, `signout`, `me`, `csrf`, `verify_email` (`views.py`) | функции `@api_view` | `/api/auth/...` | регистрация, вход, выход, текущий пользователь |
| `work_*` (`work_api.py`) | функции | `/api/auctions/{id}/work/...` | выполнение заказа после торгов |
| `my_statistics`, `admin_analytics`, `admin_export_csv`, … (`analytics.py`) | функции | `/api/my/statistics/`, `/api/admin/analytics/`, `/api/admin/reports/` | статистика и отчёты |
| `my_notifications` (`notifications.py`) | функция | `/api/notifications/` | уведомления о результатах |
| `AllUsersViewSet`, `AllAuctionsViewSet` (`admin_api.py`) | `ReadOnlyModelViewSet` | `/api/admin/users/`, `/api/admin/auctions/` | данные для администратора |
| `frontend_app` (`config/urls.py`) | функция | все остальные пути | отдаёт `index.html` для React Router |

Что делает контроллер, а что поручает другим:

- **права доступа** — через классы разрешений DRF: `Admitted` (`views.py`), `Administrator` (`admin_api.py`), `IsAuthenticated` по умолчанию (`REST_FRAMEWORK` в `settings.py`);
- **проверка формы данных** — сериализаторы `BidInput`, `DecisionInput`, `RegistrationInput`;
- **бизнес-правила** — вызов `services.*`;
- **ограничение частоты запросов** — `LoginRateThrottle`, `RegisterRateThrottle`, `VerifyRateThrottle`;
- **пагинация** — `PageNumberPagination`, по 20 записей.

### View (представление) подробно

**На сервере** представление — это **сериализаторы** (`auction/serializers.py`). Они решают, какие поля и в
каком виде увидит клиент. Пример бизнес-правила на уровне представления: `AuctionSerializer.get_winner_id`
и `get_payment_kopecks` возвращают победителя и цену **только когда статус `closed`** — до конца торгов
эти данные не раскрываются.

**На клиенте** представление — это React-приложение. Внутри него тоже есть разделение, похожее на MVC:

| Роль на клиенте | Папка / файл | Что там |
|---|---|---|
| модель данных клиента | `api/types.ts` | TypeScript-типы `Auction`, `Bid`, `User`, `AuctionStatus` — повторяют формат JSON сервера |
| доступ к данным | `api/auctions.ts`, `api/auth.ts`, `api/client.ts` | функции запросов; страницы не вызывают axios напрямую |
| контроллер экрана | `pages/*.tsx` | состояние страницы (`useState`), обработчики кнопок, загрузка данных |
| чистое отображение | `components/*.tsx` | `StatusBadge`, `KopecksInput`, `Layout` — получают данные через props |
| общее состояние | `context/AuthContext.tsx` | текущий пользователь для всего приложения (шаблон *Provider*) |
| маршрутизация | `App.tsx` | соответствие URL ↔ страница, защитники `RequireAuth`, `RequireModerator` |

### Правила зависимостей между слоями

```
frontend/pages ──▶ frontend/components
      │
      └──▶ frontend/api ── HTTP ──▶ config/urls ──▶ views / *_api ──▶ serializers
                                                          │
                                                          └──▶ services ──▶ models ──▶ PostgreSQL
management/commands ──────────────────────────────────────────▶ services
tests ──▶ (через HTTP-клиент) views   и   (напрямую) services
```

- Стрелки идут **только вниз**: модель не импортирует контроллер, сервис не знает про `request`.
- Одна бизнес-функция — много потребителей: `close_auction` вызывают и команда `close_auctions`, и тесты.
- Права проверяются **на сервере**; скрытие кнопок на клиенте — только удобство.

### Второй сценарий: закрытие торгов без HTTP

Показывает, зачем бизнес-логика вынесена из контроллера:

1. `auction/management/commands/close_auctions.py` — раз в 10 секунд ищет аукционы со статусом `open` и истёкшим `ends_at`.
2. Для каждого вызывает `services.close_auction(pk)` — **ту же функцию**, что проверяют тесты.
3. `close_auction` блокирует аукцион и участников, проверяет, что никто не заблокирован (иначе `paused`), берёт две лучшие ставки, записывает победителя и цену, пишет событие `closed` в `Event`.
4. Клиент узнаёт результат при очередном опросе (`setInterval` раз в 5 секунд в `AuctionDetailPage.tsx:79`), сериализатор теперь раскрывает `winner_id` и `payment_kopecks`.

Контроллера здесь нет вовсе — если бы правила жили в `views.py`, их пришлось бы дублировать.

### Применённые шаблоны проектирования

| Шаблон | Где в коде | Зачем |
|---|---|---|
| MVC / MTV | весь backend | разделение данных, логики обработки и отображения |
| Service Layer | `auction/services.py` | бизнес-правила в одном месте, независимо от HTTP |
| Active Record / ORM | `auction/models.py` | работа с таблицами как с объектами Python |
| Front Controller, Router | `config/urls.py`, `DefaultRouter` | единая точка маршрутизации, URL для ViewSet генерируются автоматически |
| DTO / Serializer | `auction/serializers.py` | проверка входных данных и формат выходных |
| State Machine | `Auction.Status`, `services.transition`, `WorkOrder.Status` | допустимы только описанные переходы статусов |
| Audit Log | модель `Event`, функция `event` | история всех действий с аукционом |
| Idempotency Key | `AuctionRequest`, `Bid.idempotency_key`, `WorkSubmission.idempotency_key` | повтор запроса не создаёт дубль |
| Pessimistic Locking | `select_for_update()` в `services.py`, `work_api.py` | корректная работа при одновременных запросах |
| Middleware / Chain of Responsibility | `MIDDLEWARE` в `settings.py` | сессии, CSRF, безопасность до контроллера |
| Interceptor | `api/client.ts` | CSRF-токен и повтор запроса для всех вызовов API |
| Provider / Context | `context/AuthContext.tsx` | пользователь доступен на любой странице |
| Guard | `RequireAuth`, `RequireModerator` в `App.tsx` | закрытые страницы недоступны без входа и роли |
| Background Worker | `close_auctions --loop` | закрытие торгов по времени, независимо от запросов |

### Безопасность по слоям (эшелонированная защита)

| Слой | Механизм |
|---|---|
| Клиент | защитники маршрутов, блокировка двойного клика, CSRF-заголовок `X-CSRFToken` |
| Middleware | `CsrfViewMiddleware`, сессии с cookie `HttpOnly`, `SameSite=Lax`, `Secure` и HSTS в production |
| Контроллер | классы разрешений (`Admitted`, `Administrator`), лимиты частоты, проверка типов и длины входных данных |
| Сервис | права на действие (`has_perm("auction.moderate_auction")`, нельзя ставить на свою задачу), транзакции и блокировки |
| Модель / БД | `CheckConstraint`, `UniqueConstraint`, `PROTECT` |
| Представление | сериализатор скрывает победителя и цену до закрытия; CSV-отчёт экранирует формулы (`csv_cell`) |

### Архитектура развёртывания

```
                 GitHub (репозиторий)
                   │ push в dev_any / main
        ┌──────────┴──────────────┐
        ▼                         ▼
 GitHub Actions: ci.yml     GitHub Actions: pages.yml
 тесты на PostgreSQL 16,    сборка React → GitHub Pages
 makemigrations --check,    (статический обучающий макет)
 сборка React
        │
        ▼
 Render: Docker-контейнер (Dockerfile)
 ┌───────────────────────────────────────────────┐
 │ этап 1: node:22-alpine → npm ci, npm run build│
 │ этап 2: python:3.12-slim                      │
 │   migrate → bootstrap/seed → close_auctions & │
 │   Gunicorn (WSGI) + WhiteNoise (статика React)│
 └──────────────────────┬────────────────────────┘
                        ▼
                PostgreSQL (DATABASE_URL)
```

Локально то же самое собирается через `compose.yaml`: три сервиса — `db` (PostgreSQL 16), `web` (Django)
и `worker` (закрытие торгов). Это правильнее production-схемы, где worker запущен фоном в том же контейнере.

### Сильные стороны и ограничения архитектуры

Честно о том, что уже хорошо и что можно улучшить (на защите это обычно ценят):

| Сильные стороны | Ограничения / что улучшить |
|---|---|
| бизнес-правила изолированы в `services.py` и покрыты тестами | `views.py` (`create`, `partial_update`) и `work_api.py` содержат транзакции и проверки статуса — по правилам MVC их стоит перенести в сервисы |
| целостность защищена и кодом, и ограничениями БД | одно Django-приложение `auction` на всё; выполнение работы и аналитику можно выделить в отдельные приложения |
| один домен для SPA и API — простая и безопасная авторизация через сессии | обновление результатов через опрос раз в 5 с; для мгновенных обновлений подошли бы WebSocket (Django Channels) |
| идемпотентность и блокировки — корректная работа при сбоях сети и гонках | worker закрытия торгов в production живёт в том же контейнере, что и веб-сервер |
| стандартный стек, лёгкое развёртывание через Docker | статусы местами записаны строками (`"open"`) вместо `Auction.Status.OPEN` |

### Вопросы по архитектуре, которые могут задать

- *Какая архитектура у проекта?* — Клиент-серверная: SPA на React и REST API на Django. Сервер построен по MVC (в Django — MTV) с отдельным сервисным слоем.
- *Где у вас контроллер, если в Django нет такого слова?* — Контроллер в Django называется view: `views.py`, `work_api.py`, `analytics.py`. Маршруты к ним — в `config/urls.py`.
- *Чем MTV отличается от MVC?* — Только названиями: Django View = Controller, Django Template = View. В нашем проекте вместо шаблонов отображение делает React.
- *Почему бизнес-логика не в контроллерах и не в моделях?* — Её вызывают из нескольких мест (HTTP, фоновая команда, тесты). В сервисе она написана один раз и не зависит от HTTP.
- *Почему React, а не шаблоны Django?* — Интерактивный интерфейс без перезагрузки страниц, автообновление ставок, отдельная разработка фронтенда и бэкенда параллельно двумя людьми.
- *Как фронтенд и бэкенд договорились о формате данных?* — Контракт API в `docs/API.md`, на клиенте он повторён типами в `api/types.ts`.
- *Как добавить новую функцию, например платежи?* — Модель в `models.py` (или новое приложение `payments`), правила в сервисе, контроллер и маршрут в `urls.py`, функция в `frontend/src/api/` и страница в `pages/`. Существующие слои менять не нужно.
- *Как система переживёт рост нагрузки?* — Gunicorn позволяет увеличить число воркеров; сервер не хранит состояние в памяти (сессии в БД), поэтому можно запустить несколько контейнеров; для лимитов запросов тогда понадобится общий кеш Redis.
