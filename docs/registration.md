# Регистрация пользователей через сайт

Маршруты:
- \`/register\`: форма с именем пользователя, email и паролем;
- \`POST /api/auth/register/\`: создание неподтверждённого пользователя и отправка письма;
- \`/verify-email?uid=...&token=...\`: ссылка подтверждения;
- \`POST /api/auth/verify-email/\`: подтверждение email;
- \`/login\`: вход после подтверждения.

Вход до подтверждения email запрещён действующим правилом \`eligible()\`.
Обработка ограничена 3 регистрациями и 20 проверками адреса в час на IP.
Пароль проверяется стандартными правилами Django и ограничением минимум 12 символов.

## Настройка в Render

В [Render Dashboard](https://dashboard.render.com) → REA_auction → Environment
добавьте **секретные**, не публикуемые в GitHub переменные:

- \`EMAIL_HOST\` — SMTP-сервер почтового провайдера;
- \`EMAIL_PORT\` — порт (обычно 587);
- \`EMAIL_USE_TLS=1\`, \`EMAIL_USE_SSL=0\` (или иные настройки провайдера);
- \`EMAIL_HOST_USER\` — SMTP-логин;
- \`EMAIL_HOST_PASSWORD\` — пароль SMTP или API-пароль приложения;
- \`DEFAULT_FROM_EMAIL\` — адрес отправителя, разрешённый SMTP-провайдером.

**Без SMTP в production регистрация корректно отвечает 503 и не создаёт пользователей**, чтобы не оставлять людей с неподтверждаемой почтой. В \`DEBUG=1\` письма выводятся в консоль только для локальной разработки. Для реального использования нужен SMTP-провайдер, разрешающий отправку через Render. Не присылайте пароль SMTP в чат.

Пароль не возвращается из API, в базе хранится Django-хеш, токен подтверждения ограничен сроком в 24 часа. Не добавляйте пароли в файлы репозитория.

В бесплатной конфигурации Render лимиты по IP применяются через локальный кеш Django и могут быть неполными при нескольких процессах; для масштабирования рекомендуется Redis + более строгая антиспам-защита. Рекомендуется настроить SPF/DKIM для домена отправителя и проверить доставку письма перед открытием публичной регистрации.
